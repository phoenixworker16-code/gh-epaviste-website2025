# ==========================================================
# CHAPITRE 1
# VISION PRODUIT & PHILOSOPHIE UX
# ==========================================================

## Statut

Document officiel.

Tous les assistants IA doivent respecter les règles définies dans ce document avant toute modification de l'interface utilisateur.

En cas de contradiction :

AI_RULES.md prévaut toujours.

PROJECT_ROADMAP.md définit la stratégie.

UX_UI_MASTER_SPEC.md définit la manière de concevoir l'expérience utilisateur.

---

# Mission

La mission de GH Épaviste n'est pas de posséder un simple site Internet.

Le site est un outil de communication, de confiance et de conversion.

Chaque élément de l'interface doit aider un utilisateur à résoudre rapidement un problème réel.

Le design n'est jamais décoratif.

Le design doit toujours avoir une utilité.

Chaque composant doit améliorer au moins un des objectifs suivants :

- compréhension ;
- confiance ;
- accessibilité ;
- conversion ;
- simplicité ;
- rapidité.

Si une modification n'améliore aucun de ces critères, elle ne doit pas être implémentée.

---

# Vision Produit

GH Épaviste doit devenir une référence en matière de qualité numérique dans son secteur.

Le projet privilégie :

- la qualité avant la quantité ;
- la simplicité avant la complexité ;
- la cohérence avant l'originalité ;
- l'expérience utilisateur avant les effets visuels.

Le visiteur ne doit jamais avoir à réfléchir pour comprendre comment utiliser le site.

Chaque écran doit guider naturellement l'utilisateur.

---

# Philosophie

Une interface réussie est une interface qui paraît évidente.

L'utilisateur ne doit pas avoir à apprendre comment fonctionne le site.

Il doit immédiatement comprendre :

- où il se trouve ;
- ce que propose GH Épaviste ;
- ce qu'il doit faire ensuite.

La meilleure interface est celle qui disparaît au profit du contenu.

---

# Objectif principal

Transformer un visiteur en contact qualifié.

Les objectifs commerciaux priment sur les effets graphiques.

Chaque décision doit améliorer le parcours utilisateur.

---

# Utilisateur avant technologie

Les choix techniques ne doivent jamais dégrader l'expérience utilisateur.

Une technologie complexe n'est acceptable que si elle améliore réellement l'utilisation du site.

Le projet privilégie toujours :

expérience utilisateur > technologie

---

# Mobile First

Le smartphone constitue la plateforme de référence.

Toutes les décisions de conception doivent être prises en priorité pour :

- Android
- iPhone

Le desktop représente une adaptation.

Jamais l'inverse.

---

# Compréhension immédiate

Le visiteur doit comprendre l'activité du site en moins de trois secondes.

Il doit pouvoir identifier immédiatement :

- le service proposé ;
- la zone d'intervention ;
- la proposition de valeur ;
- l'action principale.

Si ces informations ne sont pas comprises rapidement, l'interface doit être repensée.

---

# Simplicité

Chaque écran poursuit un objectif unique.

Une page ne doit jamais présenter plusieurs actions principales concurrentes.

Une seule priorité.

Un seul parcours.

Une seule décision attendue.

---

# Cohérence

Tous les composants doivent partager les mêmes règles :

- couleurs ;
- typographie ;
- espacements ;
- animations ;
- comportement.

L'utilisateur ne doit jamais avoir l'impression de changer d'application en naviguant.

---

# Lisibilité

La lecture doit rester confortable sur tous les appareils.

Le contenu doit être facilement compréhensible.

Le design ne doit jamais nuire au texte.

Le texte reste l'élément principal de communication.

---

# Confiance

Le site doit inspirer confiance dès les premières secondes.

Chaque élément doit renforcer cette perception.

Par exemple :

- design propre ;
- informations cohérentes ;
- numéro de téléphone visible ;
- contenu professionnel ;
- navigation fluide.

---

# Rapidité

L'utilisateur doit toujours pouvoir effectuer son action rapidement.

Aucune étape inutile.

Aucune distraction.

Aucun obstacle.

---

# Accessibilité

Le projet vise une accessibilité conforme aux recommandations WCAG 2.2 niveau AA minimum.

L'accessibilité n'est pas une fonctionnalité.

Elle fait partie intégrante de la qualité du produit.

---

# Performance

Les performances font partie de l'expérience utilisateur.

Une interface lente est une mauvaise interface.

Les optimisations graphiques ne doivent jamais dégrader :

- Lighthouse ;
- Core Web Vitals ;
- temps de chargement.

---

# Conversion

Chaque composant doit participer à la conversion.

Même un simple titre.

Même une carte.

Même un espace blanc.

Chaque élément possède une fonction.

Aucun composant décoratif inutile.

---

# Design émotionnel

Le design doit inspirer :

- confiance ;
- professionnalisme ;
- rapidité ;
- sérénité.

Il ne doit jamais provoquer :

- confusion ;
- surcharge visuelle ;
- hésitation.

---

# Évolution

Le projet est conçu pour évoluer pendant plusieurs années.

Les décisions doivent rester compatibles avec les futures évolutions.

La maintenabilité est une priorité.

---

# Qualité

Chaque amélioration doit être mesurable.

Une modification ne doit jamais être appliquée uniquement parce qu'elle paraît plus jolie.

Toute décision doit pouvoir être justifiée par :

- une meilleure compréhension ;
- une meilleure accessibilité ;
- une meilleure conversion ;
- une meilleure cohérence ;
- une meilleure ergonomie.

---

# Principes fondamentaux

Le projet applique les principes suivants :

- Mobile First
- User Centered Design
- Progressive Enhancement
- Consistency
- Accessibility by Design
- Performance by Design
- Content First
- Conversion First

Ces principes sont obligatoires.

Ils priment sur les préférences personnelles.

---

# Vision à long terme

GH Épaviste doit devenir une référence technique et ergonomique dans son secteur.

Le projet privilégie une amélioration continue.

Chaque nouvelle version doit être meilleure que la précédente.

Aucune régression volontaire n'est acceptable.

---

# CHAPITRE 2
# PRINCIPES FONDAMENTAUX UX
# ==========================================================

## Objectif

Ce chapitre définit les principes de conception obligatoires.

Tous les composants, toutes les pages et toutes les futures évolutions doivent respecter ces règles.

Ces principes priment sur les préférences personnelles.

Ils doivent guider chaque décision de design.

---

# L'utilisateur est toujours la priorité

Aucune décision ne doit être prise uniquement pour satisfaire une préférence graphique.

Chaque modification doit améliorer l'expérience du visiteur.

Toujours se demander :

Pourquoi cette modification améliore-t-elle l'expérience utilisateur ?

Si la réponse n'est pas claire :

Ne pas implémenter la modification.

---

# Le design résout un problème

Le design n'est pas une décoration.

Le design est une solution.

Chaque composant doit résoudre un problème réel.

Exemples :

Un bouton doit permettre d'agir.

Une carte doit organiser l'information.

Une icône doit améliorer la compréhension.

Une couleur doit créer une hiérarchie.

Un espace blanc doit améliorer la lecture.

---

# Une seule décision par écran

Chaque écran doit conduire vers une action principale.

Ne jamais proposer plusieurs objectifs concurrents.

Exemple :

Accueil :

✔ Appeler

✔ Demander un enlèvement

Éviter :

Télécharger

Partager

Créer un compte

S'abonner

Suivre Facebook

Faire un don

Plus il existe de décisions simultanées,

plus l'utilisateur hésite.

---

# Réduire la charge cognitive

L'utilisateur ne doit jamais réfléchir inutilement.

Le site doit répondre naturellement aux questions :

Qui êtes-vous ?

Que proposez-vous ?

Où intervenez-vous ?

Que dois-je faire maintenant ?

Si une page demande un effort de compréhension,

elle doit être simplifiée.

---

# Le contenu avant les effets

Les animations, les dégradés et les effets visuels ne doivent jamais masquer le contenu.

Le texte reste prioritaire.

Le contenu est le principal moyen de communication.

---

# La cohérence est obligatoire

Les utilisateurs apprennent rapidement le fonctionnement d'un site.

Chaque différence inutile crée une confusion.

Tous les composants similaires doivent :

avoir le même comportement,

les mêmes espacements,

la même logique,

la même animation,

la même hiérarchie.

---

# Les conventions sont préférables à l'originalité

Ne jamais réinventer une interface connue.

Un utilisateur sait déjà :

où chercher un menu,

où trouver un bouton,

où chercher un formulaire.

Respecter ces habitudes.

Une innovation n'est acceptable que si elle améliore réellement l'expérience.

---

# Le feedback est obligatoire

Chaque interaction doit produire une réponse visible.

Exemples :

hover

focus

clic

chargement

succès

erreur

L'utilisateur ne doit jamais se demander si son action a été prise en compte.

---

# Les erreurs doivent être évitées

La meilleure erreur est celle qui n'arrive jamais.

Prévenir plutôt que corriger.

Par exemple :

validation immédiate d'un formulaire,

boutons désactivés si nécessaire,

messages clairs,

libellés explicites.

---

# La simplicité est une force

Chaque élément doit avoir une utilité.

Si un composant n'apporte aucune valeur,

il doit être supprimé.

Le minimalisme ne consiste pas à retirer des éléments.

Il consiste à retirer uniquement ce qui est inutile.

---

# L'expérience doit être prévisible

Les utilisateurs aiment les interfaces prévisibles.

Un bouton doit toujours agir comme un bouton.

Un lien doit toujours agir comme un lien.

Une carte interactive doit toujours réagir de la même manière.

Aucun comportement surprenant.

---

# Les actions importantes doivent être visibles

Les actions principales doivent être immédiatement identifiables.

Le visiteur ne doit jamais chercher :

le téléphone,

le formulaire,

le bouton principal,

les informations essentielles.

---

# La confiance est une priorité UX

Le design influence directement la confiance.

Une interface propre inspire davantage confiance qu'une interface désorganisée.

Chaque page doit transmettre :

professionnalisme,

fiabilité,

stabilité,

transparence.

---

# Les informations importantes en premier

Toujours appliquer une hiérarchie.

Le visiteur doit voir :

1. le titre

2. la proposition de valeur

3. l'action principale

4. les informations secondaires

Jamais l'inverse.

---

# Les décisions doivent être rapides

Le parcours utilisateur doit être court.

Chaque clic inutile augmente le risque d'abandon.

Toujours rechercher le chemin le plus simple.

---

# Le mobile est la référence

Toutes les décisions UX sont prises d'abord pour :

Android

iPhone

Ensuite seulement :

Tablette

Desktop

Grand écran

---

# Les gestes naturels

Le site doit respecter les habitudes des utilisateurs mobiles.

Les éléments interactifs doivent être facilement accessibles au pouce.

Éviter les actions nécessitant une grande précision.

---

# Les formulaires doivent être simples

Chaque champ supplémentaire réduit le taux de conversion.

Demander uniquement les informations réellement nécessaires.

Éviter les formulaires longs.

---

# La lecture doit être fluide

Les paragraphes doivent rester courts.

Les phrases doivent être simples.

Les titres doivent annoncer clairement leur contenu.

Le visiteur doit pouvoir scanner rapidement une page.

---

# L'émotion est importante

Une bonne interface doit rassurer.

Le visiteur doit ressentir :

calme,

maîtrise,

rapidité,

professionnalisme.

Jamais :

stress,

confusion,

incertitude.

---

# Les performances font partie de l'UX

Une page rapide est plus agréable.

Une animation lente dégrade l'expérience.

Les performances sont une composante de l'expérience utilisateur.

---

# Les micro-interactions

Les animations doivent être discrètes.

Elles servent à :

guider,

confirmer,

attirer l'attention,

rassurer.

Jamais à distraire.

---

# Les améliorations doivent être mesurables

Une modification UX doit améliorer au moins un indicateur :

compréhension,

conversion,

temps d'action,

accessibilité,

lisibilité,

confiance,

navigation.

Une amélioration non mesurable doit être remise en question.

---

# Les préférences personnelles sont interdites

Les décisions ne doivent jamais être justifiées par :

"je préfère"

"je trouve ça plus joli"

"c'est à la mode"

Les décisions doivent être justifiées par :

les bonnes pratiques,

les tests,

les recommandations,

les standards,

les objectifs du projet.

---

# Les références officielles

Les assistants IA doivent s'inspirer des recommandations suivantes :

Google Material Design

Apple Human Interface Guidelines

WCAG 2.2

Nielsen Norman Group

Baymard Institute

Laws of UX

Ces références doivent guider les décisions sans être copiées mot à mot.

---

# Principe final

Chaque composant doit répondre à cette question :

Est-ce que cette interface aide réellement un utilisateur à résoudre son problème plus rapidement, plus facilement et avec davantage de confiance ?

Si la réponse est non,

la conception doit être revue.

# CHAPITRE 3
# MOBILE FIRST & EXPÉRIENCE MOBILE
# ==========================================================

## Objectif

Le smartphone constitue la plateforme de référence du projet.

Toutes les décisions UX et UI doivent être prises en priorité pour un utilisateur utilisant un téléphone mobile.

Le desktop est une adaptation.

Jamais l'inverse.

---

# Philosophie Mobile First

GH Épaviste est un service d'intervention.

Les utilisateurs ne consultent généralement pas le site depuis un bureau.

Ils sont souvent :

- devant leur véhicule ;
- sur un parking ;
- sur le bord d'une route ;
- dans un garage ;
- dans une cour ;
- avec peu de temps disponible.

Le design doit tenir compte de cette réalité.

---

# Priorité officielle

Ordre de conception :

1. Android

2. iPhone

3. Tablette

4. Desktop

5. Très grands écrans

Toute nouvelle interface doit respecter cet ordre.

---

# Les scénarios d'utilisation

Les assistants IA doivent toujours imaginer les situations suivantes.

Cas n°1

Un utilisateur est devant sa voiture.

Il ouvre Google.

Il clique sur GH Épaviste.

Il doit comprendre immédiatement :

- où il est ;
- ce que propose GH Épaviste ;
- comment appeler.

---

Cas n°2

Un utilisateur compare plusieurs épavistes.

Le site doit inspirer davantage confiance que les concurrents.

---

Cas n°3

L'utilisateur utilise une seule main.

Tous les éléments importants doivent rester facilement accessibles.

---

Cas n°4

L'utilisateur est pressé.

Chaque seconde compte.

Chaque clic inutile réduit les chances de conversion.

---

# Une seule main

Toutes les interfaces doivent pouvoir être utilisées avec une seule main.

Les assistants IA doivent privilégier :

- les gros boutons ;
- les actions simples ;
- les gestes naturels.

Éviter les interactions nécessitant une grande précision.

---

# Zone de confort du pouce

Les principaux boutons doivent être placés dans les zones naturellement accessibles au pouce.

Éviter les actions critiques placées dans des zones difficiles d'accès.

---

# Temps de compréhension

Objectif :

Le visiteur comprend le service proposé en moins de 3 secondes.

Le visiteur sait comment contacter GH Épaviste en moins de 5 secondes.

Si ces objectifs ne sont pas atteints :

FAIL.

---

# Téléphone prioritaire

Le numéro de téléphone est le CTA principal.

Il doit être :

visible,

cliquable,

lisible,

accessible rapidement.

Le téléphone reste prioritaire sur tous les autres moyens de contact.

---

# Taille minimale des zones tactiles

Toutes les zones interactives doivent mesurer au minimum :

48 × 48 px.

Objectif recommandé :

56 × 56 px.

Cette règle concerne :

- boutons ;
- liens importants ;
- icônes interactives ;
- boutons d'appel ;
- boutons WhatsApp ;
- menu mobile.

---

# Espacement tactile

Les boutons ne doivent jamais être collés les uns aux autres.

Toujours prévoir un espacement suffisant afin d'éviter les erreurs de manipulation.

---

# Navigation

Le menu mobile doit être immédiatement compréhensible.

L'utilisateur doit pouvoir accéder rapidement :

Accueil

Services

Zones d'intervention

Guide

Contact

Le menu ne doit jamais devenir une liste interminable.

---

# Sticky CTA

Lorsque cela améliore réellement la conversion,

un bouton d'appel fixe peut être utilisé.

Conditions :

ne jamais masquer le contenu,

ne jamais gêner la navigation,

rester discret.

---

# Hero Mobile

Le Hero doit être pensé d'abord pour un écran mobile.

Il doit afficher immédiatement :

Titre

Sous-titre

CTA principal

Le contenu essentiel doit rester visible sans avoir besoin de scroller sur la majorité des smartphones.

---

# Priorité visuelle

Ordre recommandé :

Titre

↓

Proposition de valeur

↓

Bouton principal

↓

Informations secondaires

↓

Illustration

Jamais l'inverse.

---

# Images

Les images doivent améliorer la compréhension.

Éviter les images uniquement décoratives.

Chaque image doit répondre à un objectif :

rassurer,

illustrer,

expliquer,

humaniser.

---

# Texte

Le texte doit rester court.

Privilégier :

phrases simples,

paragraphes courts,

titres explicites.

Éviter les blocs de texte très longs sur mobile.

---

# Scroll

Le scroll est naturel.

Il ne doit pas être considéré comme un problème.

En revanche,

l'utilisateur ne doit jamais devoir scroller pour comprendre l'activité principale.

---

# Cartes

Les cartes doivent rester lisibles.

Prévoir :

padding généreux,

espacement régulier,

coins arrondis,

ombre discrète.

Une carte ne doit jamais sembler "serrée".

---

# Formulaires

Le formulaire doit demander uniquement les informations réellement nécessaires.

Limiter le nombre de champs.

Chaque champ doit être facile à utiliser sur mobile.

---

# Clavier

Le type de clavier doit être adapté.

Téléphone

→ clavier numérique.

Email

→ clavier email.

Texte

→ clavier standard.

---

# Performance

Les appareils mobiles peuvent être moins puissants.

Les animations doivent rester fluides.

Les composants inutiles doivent être évités.

---

# Réseau mobile

Le site doit rester agréable même avec une connexion moyenne.

Limiter :

les images lourdes,

les vidéos automatiques,

les scripts inutiles.

---

# Safe Areas

Le contenu ne doit jamais être masqué par :

Dynamic Island,

encoches,

barres système,

gestes de navigation.

Les marges de sécurité doivent être respectées.

---

# Orientation

Le site doit fonctionner correctement en :

portrait,

paysage.

Aucune fonctionnalité ne doit dépendre d'une orientation précise.

---

# Android

Le design doit être compatible avec les principales tailles d'écran Android.

Ne jamais optimiser uniquement pour un seul modèle.

Tester différentes largeurs.

---

# iPhone

Le design doit respecter les habitudes des utilisateurs iPhone.

Les interactions doivent rester naturelles.

Les marges doivent tenir compte des Safe Areas.

---

# Tablette

La tablette ne constitue pas la cible principale.

Elle doit néanmoins offrir une expérience confortable.

Éviter les interfaces simplement agrandies.

---

# Desktop

Le desktop représente une adaptation.

Ne jamais ajouter des éléments uniquement parce que davantage d'espace est disponible.

L'espace supplémentaire doit améliorer la lisibilité.

Pas la complexité.

---

# Responsive

Chaque changement doit être testé sur plusieurs tailles d'écran.

Aucun composant ne doit casser la mise en page.

Le responsive est obligatoire.

---

# Validation Mobile

Avant chaque validation,

les assistants IA doivent vérifier :

✔ lisibilité

✔ navigation

✔ boutons

✔ formulaires

✔ Hero

✔ CTA

✔ menu

✔ footer

✔ performances

✔ accessibilité

---

# Principe final

Chaque décision doit répondre à cette question :

Un utilisateur qui découvre GH Épaviste sur son smartphone peut-il comprendre le service et contacter l'entreprise en quelques secondes, sans hésitation et sans difficulté ?

Si la réponse est non,

la conception doit être revue.

# CHAPITRE 4
# RESPONSIVE ENGINEERING
# ANDROID • IPHONE • TABLETTE • DESKTOP

## Objectif

Toutes les interfaces développées pour GH Épaviste doivent offrir une expérience cohérente sur l'ensemble des appareils modernes.

Le Responsive Design n'est pas une étape finale.

Il fait partie intégrante de la conception.

Chaque composant est pensé responsive dès sa création.

Jamais après.

---

# Principe fondamental

Le Responsive Design ne consiste pas à faire "rentrer" le site dans un écran.

Le Responsive Design consiste à adapter intelligemment l'expérience utilisateur.

Chaque écran possède ses contraintes.

Chaque appareil possède ses usages.

L'interface doit respecter ces différences.

---

# Plateformes officielles

Les interfaces doivent fonctionner correctement sur :

Android

iPhone

iPad

Tablettes Android

Laptop

Desktop

UltraWide

Aucun appareil ne constitue une exception.

---

# Breakpoints

Les assistants IA doivent utiliser des breakpoints cohérents.

Exemple recommandé :

320 px

375 px

390 px

414 px

480 px

640 px

768 px

820 px

1024 px

1280 px

1440 px

1536 px

1920 px

Ces valeurs peuvent évoluer mais doivent rester cohérentes dans tout le projet.

---

# Largeur maximale

Le contenu principal ne doit jamais devenir difficile à lire.

Une largeur maximale doit être définie.

Le texte ne doit jamais s'étendre sur toute la largeur d'un écran UltraWide.

La lisibilité reste prioritaire.

---

# Colonnes

Le nombre de colonnes dépend du contexte.

Mobile

1 colonne

Tablette

1 ou 2 colonnes

Desktop

2 ou 3 colonnes

Très grand écran

Ne jamais ajouter des colonnes uniquement parce qu'il reste de la place.

---

# Espacement

Le Responsive Design ne consiste pas uniquement à modifier la largeur.

Les espacements doivent également évoluer.

Padding

Margin

Gap

Hauteur des sections

Largeur des cartes

Toutes ces valeurs doivent être adaptées selon le contexte.

---

# Grille

Toutes les pages doivent utiliser une grille cohérente.

Les composants doivent s'aligner naturellement.

Éviter les alignements approximatifs.

Les ruptures de grille sont interdites.

---

# Hiérarchie

La hiérarchie visuelle doit rester identique sur tous les appareils.

Le titre principal reste toujours prioritaire.

Les CTA restent visibles.

Le contenu secondaire reste secondaire.

Le responsive ne doit jamais inverser les priorités.

---

# Images

Les images doivent rester :

nettes,

légères,

adaptatives.

Éviter :

les images étirées,

compressées,

déformées,

pixelisées.

---

# Typographie Responsive

La taille du texte doit évoluer progressivement.

Jamais brutalement.

Les titres restent dominants.

Le texte reste confortable.

Éviter les changements de taille excessifs entre deux breakpoints.

---

# Longueur des lignes

Une ligne trop longue fatigue la lecture.

Une ligne trop courte ralentit également la lecture.

L'objectif est une longueur confortable.

La largeur du contenu doit être adaptée.

---

# Boutons

Les boutons doivent conserver une taille confortable.

Ils ne doivent jamais devenir :

trop petits,

trop proches,

trop larges,

ou disproportionnés.

---

# Icônes

Les icônes doivent évoluer avec l'interface.

Une icône minuscule sur un grand écran paraît perdue.

Une icône géante sur mobile devient envahissante.

Le dimensionnement doit rester harmonieux.

---

# Header

Le Header doit rester stable.

Le changement entre Desktop et Mobile ne doit jamais perturber l'utilisateur.

Le menu mobile doit être immédiatement identifiable.

---

# Hero

Le Hero doit conserver la même logique.

Desktop

↓

plus d'espace

Mobile

↓

plus de simplicité

Jamais davantage de contenu.

---

# Cartes

Les cartes doivent conserver :

leurs proportions,

leurs espacements,

leurs comportements.

Le Responsive Design ne doit pas modifier leur identité.

---

# Footer

Le Footer peut changer de disposition.

Mais il doit toujours présenter les mêmes informations essentielles.

Aucun contenu important ne doit disparaître.

---

# Formulaires

Les champs doivent rester :

alignés,

lisibles,

faciles à sélectionner.

Les erreurs doivent rester visibles.

Les messages doivent rester compréhensibles.

---

# Navigation

La navigation doit fonctionner naturellement.

Aucun menu ne doit devenir inaccessible.

Les éléments interactifs doivent toujours rester visibles.

---

# Orientation

## Objectif

Le CTA (Call To Action) représente le point de conversion principal.

Sa mission est de transformer une intention en action.

Un excellent CTA ne pousse pas l'utilisateur.

Il lui montre naturellement la prochaine étape.

Le CTA doit supprimer les hésitations.

Jamais en créer.

---

# Mission

Le CTA doit répondre immédiatement à la question :

"Que dois-je faire maintenant ?"

Si cette réponse n'est pas évidente,

le composant doit être repensé.

---

# Psychologie utilisateur

Lorsqu'un visiteur arrive sur GH Épaviste,

il pense généralement :

Ma voiture est inutilisable.

Je cherche une solution.

Est-ce une entreprise sérieuse ?

Comment les contacter ?

Combien de temps cela va prendre ?

Le CTA doit répondre à cette réflexion.

Pas à celle du développeur.

---

# Une seule action principale

Chaque écran possède un seul CTA principal.

Jamais plusieurs.

Le cerveau humain hésite lorsqu'il doit choisir entre plusieurs actions importantes.

Plus il existe de CTA principaux,

plus le taux de conversion diminue.

---

# Priorité

Pour GH Épaviste,

l'ordre des CTA est :

1.

Téléphoner

↓

2.

Demander un enlèvement

↓

3.

Obtenir plus d'informations

↓

4.

Découvrir les services

Cet ordre ne doit pas être inversé.

---

# CTA principal

Le CTA principal doit :

être visible immédiatement,

être compréhensible,

être rassurant,

être facile à cliquer.

Le visiteur ne doit jamais chercher le bouton principal.

---

# CTA secondaire

Le CTA secondaire complète le parcours.

Il ne concurrence jamais le CTA principal.

Sa couleur,

sa taille

et son contraste

doivent rester légèrement inférieurs.

---

# Libellé

Le texte d'un CTA doit être explicite.

Toujours privilégier un verbe d'action.

Exemples :

Appeler maintenant

Demander un enlèvement

Nous contacter

Obtenir un devis

Éviter :

Cliquez ici

En savoir plus

Continuer

Suivant

Valider

Ces libellés sont trop génériques.

---

# Clarté

Le visiteur doit comprendre immédiatement ce qu'il se passera après le clic.

Aucune surprise.

Aucune ambiguïté.

---

# Taille

Les CTA doivent rester confortables.

Minimum :

48 × 48 px.

Recommandé :

56 px.

Les petits boutons sont interdits.

---

# Espacement

Le CTA doit respirer.

Éviter :

boutons collés,

CTA enfermés dans des blocs trop serrés,

manque de marges.

Le bouton doit attirer naturellement le regard.

---

# Couleur

Le CTA principal utilise la couleur d'accent officielle.

Cette couleur est réservée aux actions importantes.

Ne jamais utiliser cette couleur pour des éléments secondaires.

---

# Contraste

Le contraste doit respecter WCAG 2.2 AA minimum.

Le bouton doit rester parfaitement lisible :

en plein soleil,

sur smartphone,

sur desktop,

en mode sombre si applicable.

---

# Position

Le CTA principal doit apparaître :

dans le Hero,

dans les sections importantes,

à la fin des contenus longs.

Ne jamais obliger l'utilisateur à revenir en haut de la page.

---

# Répétition

Le CTA peut être répété.

Mais uniquement lorsque cela améliore réellement le parcours.

Éviter les répétitions inutiles.

---

# Téléphone

Le téléphone constitue le CTA principal du projet.

Chaque numéro doit être :

cliquable,

lisible,

facile à reconnaître.

Utiliser le protocole :

tel:

sur toutes les plateformes.

---

# Icône

Une icône peut accompagner le CTA.

Elle doit améliorer la compréhension.

Jamais détourner l'attention.

---

# États interactifs

Chaque CTA possède :

Normal

Hover

Focus

Active

Disabled

Loading

Success si nécessaire.

Aucun état ne doit être oublié.

---

# Feedback

Après un clic,

l'utilisateur doit recevoir une confirmation.

Exemples :

animation légère,

état de chargement,

confirmation visuelle.

Le doute est interdit.

---

# Temps de réaction

Les réactions doivent être immédiates.

Éviter les délais perceptibles.

Le visiteur doit sentir que son action a été prise en compte.

---

# Animation

Les animations doivent être discrètes.

Objectif :

attirer l'attention,

confirmer le clic,

rassurer.

Jamais distraire.

---

# Mobile

Le CTA doit rester facilement accessible avec une seule main.

Les boutons situés dans des zones difficiles d'accès doivent être évités.

---

# Desktop

Le CTA reste visible.

Il ne doit jamais sembler perdu dans un grand espace vide.

---

# Hiérarchie

Le CTA principal domine toujours.

Les CTA secondaires restent secondaires.

Les liens simples restent tertiaires.

La hiérarchie doit être immédiatement compréhensible.

---

# Charge cognitive

Le visiteur ne doit jamais devoir choisir entre plusieurs actions importantes.

Réduire le nombre de décisions.

Simplifier.

Guider.

---

# Formulation

Toujours parler du bénéfice utilisateur.

Éviter les formulations centrées sur l'entreprise.

Le CTA doit répondre au besoin du visiteur.

---

# Cohérence

Tous les CTA du site doivent partager :

la même forme,

la même animation,

les mêmes couleurs,

la même logique,

les mêmes états.

Le visiteur doit reconnaître immédiatement une action principale.

---

# Erreurs interdites

Ne jamais :

Afficher plusieurs CTA principaux côte à côte.

Utiliser des couleurs aléatoires.

Employer des textes vagues.

Créer des boutons trop petits.

Masquer le CTA principal.

Changer constamment le style des boutons.

Multiplier les animations.

Utiliser des effets visuels qui ralentissent la lecture.

---

# Validation

Avant validation,

les assistants IA doivent vérifier :

✔ CTA immédiatement visible

✔ Texte explicite

✔ Taille tactile conforme

✔ Contraste WCAG

✔ Responsive validé

✔ Android validé

✔ iPhone validé

✔ États interactifs présents

✔ Animation discrète

✔ Hiérarchie respectée

✔ Performance préservée

✔ Accessibilité validée

---

# KPI

Le CTA est considéré comme réussi lorsque :

Le visiteur identifie immédiatement l'action principale.

Le bouton attire naturellement le regard.

Le texte est compris sans réflexion.

Le clic est facile sur smartphone.

Le CTA inspire confiance.

Le parcours utilisateur reste fluide.

---

# Principe final

Un excellent CTA ne force jamais l'utilisateur.

Il lui donne simplement envie de passer à l'action.

Il réduit les hésitations,

renforce la confiance,

et transforme une intention en contact.

Le CTA est la conséquence logique d'une bonne expérience utilisateur,

jamais une tentative de persuasion artificielle.

## Objectif

La typographie constitue le principal moyen de communication entre GH Épaviste et ses visiteurs.

Elle ne sert pas uniquement à afficher du texte.

Elle organise l'information.

Elle guide le regard.

Elle crée une hiérarchie.

Elle inspire confiance.

Une bonne typographie réduit l'effort de lecture.

Une mauvaise typographie augmente la fatigue cognitive.

---

# Mission

La mission de la typographie est de permettre au visiteur de :

comprendre rapidement,

scanner facilement,

lire confortablement,

agir sans hésitation.

Le texte est l'interface.

Le design doit servir le contenu.

---

# Philosophie

Le visiteur ne vient pas admirer une police.

Il vient chercher une information.

La typographie doit donc devenir invisible.

Si le visiteur remarque la police avant le contenu,

la conception doit être revue.

---

# Priorité

L'ordre de priorité est :

Compréhension

↓

Lisibilité

↓

Hiérarchie

↓

Esthétique

Jamais l'inverse.

---

# Police principale

Le projet doit utiliser une seule famille typographique principale.

Une seconde famille peut être utilisée uniquement si une justification claire existe.

Multiplier les polices crée une impression d'amateurisme.

---

# Lisibilité

Toutes les tailles de texte doivent rester lisibles sur :

Android,

iPhone,

Tablette,

Desktop.

Le confort de lecture est prioritaire.

---

# Taille minimale

Le texte courant ne doit jamais être inférieur à 16 px sur mobile.

Recommandation :

16 à 18 px.

Le texte plus petit est réservé aux informations secondaires.

# Hauteur de ligne

dégradés complexes,

# Mission

Le Layout organise l'information.

Les espacements créent des respirations.

La grille apporte de la cohérence.

L'objectif est de réduire la charge cognitive.

L'espace vide améliore :

la lecture,

la compréhension,

la hiérarchie,

la confiance.

# Psychologie utilisateur

Le cerveau humain regroupe naturellement les éléments proches.

Il sépare naturellement les éléments éloignés.

Le Layout doit utiliser ce comportement.

Les espacements deviennent donc un outil de communication.

---

# Principe fondamental

Chaque élément doit avoir suffisamment d'espace pour exister.

Aucun composant ne doit sembler enfermé.

Aucun bloc ne doit sembler perdu.

Le rythme visuel doit rester constant.

---

# Système de grille

Toutes les pages utilisent une grille commune.

La grille garantit :

alignements,

cohérence,

évolutivité,

lisibilité.

Les composants ne doivent jamais casser cette grille.

---

# Conteneur principal

Le contenu doit être centré.

Une largeur maximale doit être définie.

Le texte ne doit jamais occuper toute la largeur d'un écran très large.

La lecture doit rester confortable.

Mobile

1 colonne.

1 à 2 colonnes.

2 à 3 colonnes selon le contenu.

UltraWide

Éviter les valeurs arbitraires.

# Espacement interne

Le padding donne de l'air au contenu.

Le contenu ne doit jamais toucher les bords d'un composant.

Les paddings doivent rester cohérents entre les composants similaires.

---

# Espacement externe

Les marges séparent les composants.

Deux sections différentes doivent être clairement distinguées.

Formulaires

# Proximité

Les éléments liés doivent rester proches.

Les éléments différents doivent être séparés.

Le Layout doit refléter la logique du contenu.

---

# Sections

Une section ne doit jamais mélanger plusieurs sujets.

Les séparations doivent rester claires.

# Largeur des contenus

Le contenu reste prioritaire.

# CTA

## Objectif

Le rôle d'une IA n'est pas uniquement d'écrire du code.

---

# Mission

Quels sont les risques ?

---

# Philosophie

Une bonne décision est une décision qui améliore durablement le produit.

Les préférences personnelles ne constituent jamais un argument.

Toutes les décisions doivent être fondées sur :

les besoins utilisateur,

les objectifs métier,

la qualité technique,

la cohérence du Design System,

la performance,

l'accessibilité,

la maintenabilité.

---

# Principe n°1

Résoudre un problème réel.

Une fonctionnalité ne doit jamais être développée uniquement parce qu'elle est intéressante.

Chaque évolution répond à un besoin identifié.

---

# Principe n°2

Toujours rechercher la solution la plus simple.

La simplicité est privilégiée.

Les solutions complexes nécessitent une justification.

---

# Principe n°3

Ne jamais casser une fonctionnalité existante.

Toute modification doit préserver les comportements validés.

Les régressions sont interdites.

---

# Principe n°4

Réutiliser avant de créer.

Avant de créer un nouveau composant :

chercher un composant existant,

chercher un Design Token,

chercher une règle déjà définie.

La duplication est interdite lorsqu'une solution réutilisable existe.

---

# Principe n°5

Le Mobile First prévaut.

En cas de conflit entre Desktop et Mobile,

la version Mobile est prioritaire.

Les optimisations sont conçues d'abord pour Android et iPhone.

---

# Principe n°6

La confiance prévaut sur le marketing.

Les assistants IA ne doivent jamais :

exagérer,

inventer,

sur-promettre,

ou afficher des informations non vérifiables.

Toute affirmation doit pouvoir être démontrée.

---

# Principe n°7

La performance est une fonctionnalité.

Toute évolution doit préserver :

les Core Web Vitals,

la vitesse perçue,

la fluidité,

la réactivité.

---

# Principe n°8

L'accessibilité est obligatoire.

Une amélioration graphique qui réduit l'accessibilité doit être refusée.

Les critères WCAG 2.2 AA constituent le minimum.

---

# Principe n°9

La cohérence prévaut.

Une bonne idée isolée peut être refusée si elle rompt l'unité du Design System.

La cohérence globale est plus importante qu'une optimisation locale.

---

# Principe n°10

Documenter les compromis.

Si une décision implique un compromis,

l'assistant IA doit documenter :

le bénéfice,

le coût,

les risques,

les alternatives envisagées.

Chaque mise en production doit renforcer la confiance, améliorer l'expérience utilisateur et préserver la qualité du produit.

Le Framework de Production Readiness garantit que GH Épaviste évoluera de manière maîtrisée, cohérente et durable.

Aucune fonctionnalité ne doit atteindre les utilisateurs sans avoir démontré qu'elle respecte les standards définis dans l'ensemble des documents du projet.
